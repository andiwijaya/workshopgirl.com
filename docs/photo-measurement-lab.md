# Photo Measurement Lab architecture and limits

Route: `/tools/photo-measurement/`. All images, edits and processing remain in the browser tab. No backend, uploads, analytics payloads, browser persistence, external imaging service, image recognition or new dependency is used.

## Geometry and measurement

`src/lib/photo/geometry.ts` owns finite coordinates, millimetre-based scale, display units (mm, cm, m, inch), Euclidean distance, three-point angle with the second point as vertex, polyline total, simple-polygon shoelace area, and center/edge circle radius and diameter. Crossing/touching polygon edges, repeated corners, zero-length arms and nonfinite values fail visibly. Decimal output is formatting, not an accuracy guarantee.

Reference calibration is known millimetres divided by pixel distance. Editing a reference endpoint recalculates scale from the original known dimension. Changing display units does not change the underlying geometry or millimetre scale. Removing a reference makes existing lengths and areas explicitly uncalibrated; angles remain defined. Measurements sharing one scale require a common plane and approximately uniform pixel scale. Perspective, depth, lens distortion, reference error, resolution and point-placement error are explained in the page.

Rectification requires four perimeter-ordered corners of a **known rectangle** plus both real dimensions. Corner order is TL, TR, BR, BL relative to the selected surface. Both dimensions establish the metric aspect ratio; an arbitrary quadrilateral alone cannot. A normalized 8-equation Gaussian-elimination homography maps the selected source quad to a rectangle, with pivoting, invertibility and corner residual checks. Convexity, area, edge separation, dimensions and aspect ratio are validated. Destination extents may be fractional while canvas dimensions are rounded up: the transform and scalar scale use the fractional extent, avoiding artificial anisotropic metric scaling from integer rounding.

Inverse-mapped destination pixel centers receive bilinear, premultiplied-alpha samples. Outside pixels are transparent. Image correction is cropped to the chosen planar surface, not a reconstruction of the entire 3D object. Maximum corrected edge is 2,000 pixels; rectangle aspect must be between 1:20 and 20:1. Only one correction is applied per original image, avoiding chained resampling. Restore original reruns local decode from the retained File. Successful correction discards the old reference, marks and undo/redo history and initializes scale from supplied dimensions. Report notes remain. Failed/cancelled correction keeps the original image and completed edits.

## Images, workers and coordinate systems

JPEG, PNG and browser-decodable WebP signatures/dimensions are inspected before decode; MIME type or filename alone is never trusted. Input limits: 20 MiB encoded file, 32 million pixels, 12,000 pixels per edge. Header reads are bounded to 512 KiB. Pathological files whose dimensions cannot be found within that header budget fail as incomplete rather than being decoded without bounds. SVG, HTML, HEIC and other formats are rejected. Animated image formats are not an animation/documentation feature; only the decoded browser bitmap is used.

Browser `createImageBitmap` applies EXIF orientation (`from-image`) and downsamples to at most 4 million working pixels and 2,400 pixels per edge. The lab preserves the oriented original dimensions and the exact original/working x/y scale factors. Integer downsampling can introduce subpixel aspect rounding; it cannot recover the detail lost in downsampling. Original image data is not duplicated for every edit.

Decode and projective sampling run in a route-specific module worker loaded on the first image operation. No processing worker starts on an empty lab, Home, Tools, or a tutorial. OpenCV/WASM was considered and rejected for this bounded, deterministic rectangle transform: native browser decode plus a small tested mathematical sampler avoids a global multi-megabyte dependency and provides a directly testable implementation.

Chromium/Firefox use a transferred bitmap and worker OffscreenCanvas when available. The tested Windows WebKit worker lacks OffscreenCanvas, so the UI snapshots the bounded working bitmap with Canvas, transfers its RGBA ArrayBuffer, and receives a transferred corrected RGBA ArrayBuffer from the same worker. It creates the returned bitmap on the UI thread. The pixel loop remains in the worker. This fallback has bounded synchronous Canvas read/write costs; it is not advertised as entirely off-thread.

Each task terminates its worker after success, error, cancellation or 30-second timeout. Late results are closed. Replacing, restoring, closing or leaving the image closes the old bitmap. Temporary export/snapshot canvases are resized to 1×1. Download object URLs are revoked after one second, and immediately on page exit. Page exit terminates work, clears image/edit state, disconnects resize observation and cancels drawing/timers; a back/forward-cache return starts an empty session. A single animation-frame request coalesces draws. PNG exports are serialized and cancellable so repeated clicks cannot allocate parallel full-size export canvases.

All drawing and edits use working-image coordinates. One invertible scale/translation view maps between CSS pointer coordinates and the image, independent of device-pixel-ratio canvas backing size. Wheel zoom keeps its anchor; pinch keeps the two-finger midpoint while allowing translation. Resize preserves the image point at the view center. Reset view only fits the image and never changes measurements. Touch/pointer handles have an 18 CSS-pixel selection radius. Select/move, whole-line movement, point movement, keyboard arrows, explicit point coordinates, labels, delete and undo/redo are available. History retains at most 80 bounded editing states, without image buffers. Limits are 200 marks, 200 points per path and 2,000 points total; labels are 120 characters and notes 2,000.

## Exports and accessibility

Annotated PNG uses the full **working-image** dimensions, never the visible crop/zoom. It contains the image plus annotation and measurement labels, excluding editing selection handles. It is intentionally not a full-resolution original raster export. The UI states this before export.

JSON identifies `schema: workshopgirl.photo-measurement`, `version: 1`, internal millimetres, display units, original oriented/working geometry, exact source scale factors, forward/inverse rectification matrices, rectangle dimensions, calibration, per-mark working `points`, original oriented `sourcePoints`, displayed `values`, millimetre `valuesMM`, assumptions and notes. Original coordinate conversion reverses rectification first, then reverses downsampling. No image bytes or private file paths are embedded. Sanitized local filenames are limited to ASCII letters/digits/hyphen/underscore and a bounded stem. Labels, notes and filenames are rendered as text, never raw HTML.

Native labelled controls, 44-pixel minimum buttons, focus outlines, live status/errors and keyboard operations surround the canvas. The text list and exact-coordinate inputs offer a keyboard editing alternative. Identifying an object/reference in an arbitrary photograph still requires visual interpretation; screen-reader image geometry interpretation is not claimed. No certified metrology, automatic circle fitting, depth correction, calibrated camera/lens model, persistent session/import, print/PDF report, physical Android/iOS certification or native memory-peak certification is claimed.

Built-in guidance and the typed `photoMeasurement` journey link to existing clamps, jigsaw and drill-bit guides. Tools discovery, canonical metadata and the explicit sitemap register the actual route. Header/footer current state derives from the existing `/tools/` route convention.

## Validation and benchmark reproduction

- `node --test tests/photo-measurement.test.ts tests/photo-webp-header.test.ts`: deterministic grid/unit/geometry/homography/pixel/header/export/history tests, including lossy/lossless WebP header bounds.
- `npm run test:browser -- tests/photo-measurement-browser.spec.ts --output=test-results/<isolated-phase7-directory>`: Chromium desktop/mobile, Firefox desktop and WebKit desktop/mobile. Required six viewport sizes are exercised in every project. Synthetic touch PointerEvents cover the shared gesture path; these do not certify physical devices. Native wheel coordinates/deltas can be quantized or device-scale converted, so browser pointer assertions explicitly allow a small CSS-pixel placement tolerance; exact-coordinate and mathematical assertions remain tight.
- `npm run benchmark:photo`: starts an isolated local preview on port 4387, processes synthetic 6,000×4,000 images three times in each engine in one document, verifies downsampled source coordinates, records open/correction/PNG timing, 16 ms heartbeat gaps, cleanup, Chromium post-GC JS heap after each clear cycle and raw/gzip startup/worker asset sizes. Definitions and raw trials are saved to `test-results/v2-phase7/benchmark.json`. JS heap excludes native decoder/GPU/process/worker memory; the report records a separate estimated raster budget. These are local browser observations, not physical-device or certified performance results.

Browser API references checked during implementation: [createImageBitmap orientation/resize options](https://developer.mozilla.org/en-US/docs/Web/API/Window/createImageBitmap), [OffscreenCanvas](https://developer.mozilla.org/en-US/docs/Web/API/OffscreenCanvas). Feature availability is detected in the worker and was verified by actual browser tests rather than assumed from the documentation.
